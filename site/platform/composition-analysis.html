Log in Open Control Plane

Layer 02

Safe alone. Dangerous together.

Every identity system evaluates permissions one at a time. The exfiltration path only exists in the combination. Reading customer records is routine. Calling an external webhook is routine. Neither is flagged. Together they are a data-theft channel that nothing in your stack will report.

What a single-permission review sees

  crm.contacts.read        ✓ approved  — support agents need this
  http.post.external       ✓ approved  — webhook integrations need this

  Both individually justified. Both individually low risk.
  Neither flagged by IAM, CIEM, or agent identity tooling.

What composition analysis sees

  REACHABILITY PATH DETECTED

  crm.contacts.read  →  http.post.external

  Classification:  data movement to an uncontrolled destination
  Reachable in:    one agent turn, no additional capability required
  Trigger:         any instruction reaching the agent's context

  Verdict:  the pair is denied. Either capability alone is allowed.
This is the claim we lead with, because it is the one nothing else in the market makes. Identity platforms tell you an agent is over-permissioned. None of them tell you which two of its permissions form a path.

The Classes

Four kinds of reachable path.

Composition risk is not a single pattern. These are the four that matter, and each is evaluated separately.

01

Read → Egress

Any capability that returns sensitive data, paired with any capability that moves bytes outside the boundary. Email, webhook, file write to a shared mount, even a verbose log write to a third-party sink.

02

Read → Write-Back

Read a credential, a token or a configuration value, then write it somewhere it becomes reachable — a ticket comment, a shared document, an environment variable another agent can read.

03

Enumerate → Act

List every record, then perform a per-record action. Individually a lookup and an update. Combined, the ability to modify an entire table one row at a time without ever tripping a bulk-operation control.

04

Delegate → Re-Amplify

Hand a narrow capability to a sub-agent that holds a different narrow capability. Neither agent can complete the path alone. The chain can. This is why composition is evaluated across the delegation graph, not per agent.

How It Runs

Analysed offline. Enforced inline.

The expensive part happens during policy generation. The runtime check is a set lookup.

At learn time

Graph Construction

Every capability in the profile is classified by what it can read, write, enumerate or send. The reachability graph is built once, and the dangerous pairs are enumerated.

Offline. Nothing in the hot path.

At approval

Human Review

The detected paths are presented with their classification and an example of what an attacker would need to do. The reviewer decides which to block and which are genuinely required.

Required paths get a narrower form — an allowlisted destination rather than open egress.

At runtime

Session-State Check

The capability set an agent has actually exercised in this session is tracked. If invoking the next capability would complete a blocked path, the call is denied — even though that capability is in the profile.

Order matters. The check is on the path, not the permission.
