Layer 01

Ninety-four permissions. Six in use.

Scoping permissions per task is slow, so teams grant broad access and move on. The unused ones are not idle — they are available. An agent that can read every table, call every endpoint and send every email is one poisoned document away from doing all three on someone else’s behalf.

The Problem

Why nobody scopes agent permissions properly.

It is not negligence. It is that the required permission set genuinely cannot be known at design time.

01

An agent composes tools at runtime

A deterministic microservice can be scoped in advance because its call graph is fixed. An LLM agent decides which tools to invoke while it is running, based on what it reads. There is no design-time answer to scope it against.

02

The cost of being wrong is asymmetric

Too few permissions and the agent fails visibly in front of a user. Too many and nothing happens — until it does. Teams optimise for the visible failure, which means they over-grant.

03

Tools change faster than policy reviews

A new MCP server is added on Tuesday. The quarterly access review is in March. In between, nobody re-scopes anything.

The Method

Learn what it needs. Enforce exactly that.

We observe first, derive second, and enforce only after a human has approved the result.

01

Task-class grouping

Profiles are learned per task class — invoice_reconciliation, ticket_triage — not per agent instance. The same agent doing two jobs gets two profiles, and a new agent doing a known job inherits one.

02

Capability mining with support thresholds

A capability enters the policy only if it appears above a support threshold and across a minimum number of distinct sessions. One unusual run cannot introduce a permission.

03

Argument constraint induction

Beyond which tool, we learn the shape of its arguments — numeric ranges, string enums, path prefixes — and compile those into the policy. Read access to the ledger becomes read access with a row limit.

04

Human approval before enforcement

The generated policy is human-readable, with a justification line on every capability: support level, session count, and the observed taint bound. A security engineer can answer “why is this here?” without reading model internals.

Generated policy — what a security engineer reviews

task_class: invoice_reconciliation
generated_at: 2026-09-14
trace_sessions_observed: 128
confidence: high

capabilities:
  - selector: ledger.invoices.read
    support: 0.99
    distinct_sessions: 127
    max_benign_taint: 3
    arg_constraints:
      limit: { max: 500 }

  - selector: ledger.payments.read
    support: 0.87
    distinct_sessions: 111
    max_benign_taint: 1

  - selector: report.write
    support: 0.94
    distinct_sessions: 120
    max_benign_taint: 0

denied_implicitly: 88   # granted by credential, never observed in use
Every line carries its justification. Support level, session count and taint bound are printed next to each capability. A policy you cannot interrogate is a policy you cannot defend in a review.

The Guard Rails

What stops this breaking your agents.

A least-privilege system that blocks legitimate work gets switched off in a fortnight. Three mechanisms prevent that.

Guard 01

Escalation Is A First-Class Verdict

Denial is not the only answer. When an agent requests something outside its profile, the call pauses and a human is notified. Approval mints a one-shot grant for that action only.

The agent resumes. It does not fail, and the exception is recorded.

Guard 02

Long Learn Mode By Default

Enforcement does not begin until the profile reaches a confidence threshold. Where observation is thin, the system says so and keeps observing rather than enforcing a guess.

Cold start is honest. No policy is better than a wrong one.

Guard 03

Conservative Thresholds

The support threshold is tuned to favour including a borderline capability over excluding it. Breakage is the failure mode that gets a security product removed.

Target: under five percent task breakage at eighty percent permission reduction.
